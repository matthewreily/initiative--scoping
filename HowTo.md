# How to use Initiative Scoping & Cost Tracking

Task-oriented walkthroughs. Architecture, configuration keys and operational notes are in [README.md](README.md).

## Roles at a glance

Three application roles, granted in-app at `Admin → Users`:

| Task | Admin | User | Viewer |
|------|:-:|:-:|:-:|
| View initiatives, portfolio, variance, audit log | x | x | x |
| Export CSV / XLSX | x | x | x |
| Create initiatives / edit scope (phases, allocations, non-labor costs) | x | x* | |
| Request activation, change status, request re-baseline, manage members | x | x* | |
| Activate directly / approve or reject activation requests | x | | |
| Record actual adjustments on an initiative | x | x* | |
| Approve / reject re-baseline | x | | |
| Manage BUs, resource types, rate cards, sizing, vendors, cost catalog, people, work calendar | x | | |
| Import actuals, review unmapped rows | x | | |
| Manage users and access requests | x | | |

`*` also requires being a member of the initiative with the matching membership role (Owner for status/members, Owner or Contributor for scope).

### Getting access

- Anyone in the Entra tenant can sign in. Someone without a role lands on **Request access**: submit the (optional) note and wait; the page shows *pending* until an Admin decides.
- When outbound e-mail is configured — preferably **Microsoft Graph**: `Email:GraphSender` = a licensed Microsoft 365 mailbox (`graph_mail_sender` in the Terraform tfvars) plus the **`Mail.Send` application permission with admin consent** on the Entra app (`deploy/entra/register-app.sh` adds and tries to consent it), re-using the app's own `AzureAd:*` credentials; or classic SMTP (`Email:Host`, `Email:Port`, `Email:UseStartTls`, `Email:Username`, `Email:Password`, `Email:From`; `smtp = { … }` in the tfvars plus the `<name>-smtp-password` secret) — every Active Admin — and any e-mail listed in `Auth:BootstrapAdmins` — receives a message for each new access request with the requester's name, e-mail, note and a link to *Admin → Users*. Without a mail server the request is still recorded; nothing is sent and delivery problems never block the requester.
- Admins see a pending count on `Admin → Users` and **Approve** (choosing Viewer/User/Admin) or **Reject**. They can also **Add user** before that person has ever signed in – by searching the Entra directory (when enabled, see below) or by typing their e-mail (the row is linked to their Entra account at first sign-in) – change roles, **Disable**/**Enable**, or remove. An Admin cannot demote, disable or remove their own account.
- Sign-in also records each person's display name and e-mail, which is why members, *Created by*, *Requested/Decided by* and the audit log show names instead of object IDs, and why *Add member* offers a picker of known users.
- Two overrides exist for bootstrapping and compatibility: accounts listed in `Auth:BootstrapAdmins` (object ID or e-mail; `bootstrap_admins` in the Terraform tfvars) are always Admin, and Entra **app roles** (`Admin`/`User`/`Viewer`, plus the legacy `Administrator`→Admin, `InitiativeOwner`/`Contributor`/`FinancePmo`→User) still apply and win when higher than the in-app role — including for pending or disabled accounts, so remove the Entra assignment too when revoking someone.
- **Directory search** on *Add user* queries Microsoft Graph with the app's own credentials (`AzureAd:TenantId/ClientId/ClientSecret`, i.e. the same values used for sign-in) and needs the **`User.Read.All` application permission with admin consent** on the Entra app (`deploy/entra/register-app.sh` adds and tries to consent it; otherwise grant it under *App registrations → API permissions*). Until consent is granted the page explains this and the manual e-mail form still works. Set `DirectorySearch:Enabled=false` to hide the search entirely; `DirectorySearch:MaxResults` (default 20) caps the matches. Local development (`Auth:Mode=Dev`) has no directory.
- **Sign out** (top right, next to your name) ends both the app session and the Entra session, so the next visit prompts for credentials again — use it on shared computers or to switch accounts.

## 1. First-time setup (Admin)

1. **Business Units** – `Admin → Business Units`. Create one per cost centre/BU. Deactivate rather than delete once initiatives reference a BU.
2. **Disciplines** – `Admin → Disciplines` (e.g. *Engineering*, *QA*, *Product*, *Design*). Every resource type must belong to exactly one discipline, so create these first. Deactivate a discipline to hide it from new resource types; it can only be deleted once no resource type references it.
3. **Resource Types** – `Admin → Resource Types` (e.g. *Software Engineer*, *QA Analyst*, *Product Manager*), each assigned to a discipline from the list above.
4. **Vendors** – `Admin → Vendors`. One entry per external supplier (e.g. *Acme Consulting*). Vendors are a global catalog, not business units: rate-card rows, allocations and people reference a vendor whenever their class is *Vendor*. Deactivate a vendor to hide it from new selections; it can only be deleted once nothing references it.
5. **Seniority** – `Admin → Seniority`. The catalog seeds *Associate, Mid, Senior, Staff, Principal*, but any ladder works (e.g. a vendor's *Level 1 (0-2 Years)*). Each level has a sort order (used to order rate-card rows, allocations and dropdowns) and an active flag; inactive levels stay on existing rows but are no longer offered for new ones. Names are unique case-insensitively. Levels referenced by rate cards, allocations, people, templates or baselines can only be deactivated, not deleted. You rarely need to type levels by hand: **rate-card and People CSV imports add any unknown Seniority name to the catalog automatically** (audited, appended after the current highest sort order) – so different vendors' rate cards import as-is, and their levels then appear in the allocation form. Import is still all-or-nothing: a file rejected for any other reason adds no levels.
6. **Rate Card** – `Admin → Rate Cards → New`. Give it a name and effective start date, then add entries: one row per *Resource type × Seniority × Location × Internal/Vendor (× Vendor)*. Rates are global – one card prices every business unit and initiative. For *Vendor* rows pick a specific vendor, or leave it blank for a generic vendor rate that applies to any vendor without its own row (a vendor-specific row always wins). Use *Import CSV* for bulk entry (download the template from the card page); the optional `Vendor` column holds the vendor name and legacy files with a `BusinessUnit` column still import (the column is ignored). **Unknown `ResourceType` names are added to the catalog automatically** (audited), like seniority: a new type takes the row's optional `Discipline` column (the discipline is created too if unknown), or an auto-created *Unassigned* discipline when the column is blank/absent – re-home it under `Admin → Resource Types` later. Existing types keep their discipline regardless of the column. **Publish** when complete; rates are only used from published cards. **Effective dates**: each card has an effective start and an optional effective end (last day it prices work; blank = open-ended). Every day of a phase is priced from the card whose window covers that day (latest start wins on overlap), so a phase that straddles a rate change gets a day-weighted blended hourly rate. To change rates, create a new card starting the day after the old one ends (or simply later – the later start takes over) and **Retire** the old one, choosing the effective end on the Retire button (defaults to today). A retired card with an end date still prices work dated inside its window, so earlier plans are never repriced; live forecasts only change for dates the new card covers, and committed baselines keep their snapshotted rates regardless.
7. **Sizing conversions** – `Admin → Sizing` maps T-shirt sizes / story points to total hours; **allocation templates** define how those hours split across phases and resource types.
8. **Work calendar** (needed for fixed-duration initiatives) – `Admin → Work calendar`. Set *hours per working day* (default 8) and add company holidays (weekdays only; Saturdays/Sundays are never working days). Working days = Mon–Fri minus holidays. Also pick the month the **fiscal year starts in** (default January = calendar year). With a non-January start, fiscal years are labelled by the calendar year they end in (July 2026–June 2027 = *FY2027*) and quarters are counted from the start month (*FY2027 Q1* = Jul–Sep 2026). This only affects how the *Cost by fiscal year and quarter* tables and *By fiscal period* exports group the monthly figures.
9. **Resourcing classes** – `Admin → Resourcing classes`. How a resource is sourced: the catalog seeds *Internal* (id 1) and *Vendor* (id 2) but any set works (e.g. *Offshore partner*, *Contractor*). Each class has a name (unique, case-insensitive), a **Vendor-backed** flag, a **default labor Capex %** (Internal 70, Vendor 100 out of the box), a sort order and an active flag. *Vendor-backed* is what drives vendor behaviour everywhere: the Vendor picker on rate-card rows, allocations and people only appears for vendor-backed classes, rate matching considers the vendor, and the *vendor cost / vendor hours* rollups on Details, Portfolio and Scenarios sum every vendor-backed class. New allocations start with their class's Capex default (the field follows the class while it still shows the default) and *Apply relative size* stamps it on every generated line; changing a default never touches existing lines, and non-labor lines take their default from the cost catalog item instead. Inactive classes stay on existing rows but are no longer offered for new ones; classes referenced by rate cards, allocations, people or baselines can only be deactivated, not deleted, and their Vendor-backed flag is locked. CSV files use the class **name** (`Internal`, `Vendor`, …); the legacy `InternalFte` spelling is still accepted on import.
9. **Cost catalog** (optional) – `Admin → Cost catalog`. Standard non-labor items (software licenses first; also hardware, cloud, travel, other) with vendor, billing model (*One-time*, *Monthly*, *Annual*), unit cost and a default **Capex %** (0 = all Opex, 100 = all Capex; prefilled on the initiative line, editable there), so initiatives price them consistently. Deactivate an item to hide it from new lines; it can only be deleted once no initiative references it.
10. **People** (needed for actuals) – `Admin → People`. Each person carries an external id (Planview/Jira resource id), resource type, BU, seniority, location, class and – for *Vendor* class – the vendor, so imported hours can be priced (the People CSV has matching optional `Vendor` and `Discipline` columns, and likewise adds unknown resource types/seniority levels to the catalogs). The list pages on the server (50 per page by default, 25/100 selectable; search is kept across pages) and scrolls sideways on narrow screens; bulk actions apply to the page shown.

## 2. Scope an initiative (Owner / Contributor)

1. `Initiatives → New`: name, **sponsor business unit** plus any other **participating business units** (a checklist; the sponsor is always included and cannot be removed), planning mode, target start (and target end for fixed duration), sizing method (`Direct` hours or a relative size). The size dropdown only offers sizes that have an allocation template for the chosen method; add templates under `Admin → Sizing` first.
   - **Effort-driven** (default): you type hours per allocation; phase dates are informational.
   - **Fixed duration**: the schedule is the constraint. Phases must start on the target start, run back-to-back with no gaps or overlaps, and cover the window up to the target end before the initiative can be activated. Allocation hours are *computed*, never typed: `staffing % × working days in the phase × hours/day` per person (quantity multiplies the total in the forecast). Changing a phase's dates or the target window recomputes the hours; work-calendar changes (hours/day, holidays) apply the next time an allocation or phase is saved, not retroactively to draft initiatives.
2. Add **phases** with planned start/end dates (`Add phase`). Dates can be edited later; every change is kept in the phase's date history.
3. Add **allocations**: phase, **business unit** (limited to the initiative's participating BUs; defaults to the sponsor), resource type, seniority, location, class (from `Admin → Resourcing classes`, e.g. Internal / Vendor), **vendor** (required for vendor-backed classes, hidden otherwise), quantity and hours. The BU records which unit supplies the resource (for rollups); the rate comes from the global rate card and depends on resource type, seniority, location, class and vendor only, so one initiative can mix internal staff from several BUs with people from several vendors at different rates. The form only offers resource type / seniority / location / class / vendor combinations that have a published rate on the selected phase's start date, with a live hourly-rate preview; the server rejects any other combination. To make a new resource selectable, add it under `Admin → Resource types`, then price it in a **published** rate card. If no published card is effective on the phase start date yet, every combination is offered but the allocation stays unpriced (and blocks activation) until rates exist. Hours are typed (effort-driven) or staffing % (fixed duration; defaults to 100 %, i.e. every working hour in the phase, and the form previews the resulting hours as you change the phase or %). For relative sizing choose a size and *Apply size* to generate allocations from the template, then adjust. In fixed-duration mode *Apply size* splits the target window across the template's phases in proportion to their share of hours and derives the staffing % that yields the size's hours – e.g. “L in 12 weeks needs 1 FTE”. To switch an existing effort-driven initiative to fixed duration, set a target end; existing hours are converted to an equivalent staffing % per phase.
   - **Named people** (optional): once resource type, seniority, BU and class (and vendor) are chosen, the **People** picker offers the active `Admin → People` roster members with exactly those attributes whose BU participates in the initiative – type in the search box to narrow the list by name and tick each person; the chosen people appear as chips. **Quantity is the headcount**; each named person fills one seat and any remaining seats stay generic – Details shows the names plus *+ N unassigned*. You cannot name more people than the quantity (the form raises the quantity floor as you pick). Hours are *per seat*, so a person's share of a line is the line's hours ÷ quantity. People never change the price – the rate still comes from the rate card – and the server rejects a person whose attributes differ from the allocation's or who is inactive (an already-assigned person who is later deactivated stays on the plan with an *inactive* badge). **To unassign someone** click the **×** beside their name on the Details allocation row (the seat stays and becomes unassigned; audited), or in the edit form remove them via the **×** on their chip under the People box (or *Unassign all*) and save. The **Team** tab lists named people with their per-seat hours per phase; baselines snapshot one line per named seat (plus one for the unnamed seats) with the person's name so history survives roster renames; exports, the one-pager and *Why this number?* list the people and unassigned seats. Capacity → People counts one seat's hours per named person and the unnamed seats under *Unassigned – <type>*; actuals imports match names against every person named anywhere on the initiative.
4. Watch the **Forecast** panel. Each day of a phase is priced from the published rate card covering it (a **blended** badge marks lines that straddle a rate change). A line marked **Unpriced** has no exact rate-card match – add the missing rate (or change the allocation) before activation. Click any cost (the forecast tile, a phase's cost, an allocation's or non-labor line's cost) or **Why this number?** to open a read-only breakdown: for every line the quantity × hours (and the staffing % × working days × hours/day behind them in fixed duration), the rate card(s) used with their effective windows and the day-weighted average when two cards apply, the exact reason a line is unpriced (no card covers the dates, or the card has no row for that combination), non-labor windows and billable periods, and the labor + non-labor + contingency arithmetic that gives the total – plus the delta to the current baseline.
5. Add **non-labor costs** (`Add non-labor cost`) for software licenses and other non-labor spend. Pick a catalog item (category, billing and unit cost prefill) or enter an ad-hoc line; set quantity (e.g. seats), scope it to one phase or the whole initiative, and optionally override the billing window with explicit dates. Billing is by whole periods counted from the start date – any partial month/year counts as a full one (15 Jan–14 Feb = 1 month, 15 Jan–15 Feb = 2; one-time bills once) – and the form previews the cost live. Lines recompute when phase or initiative dates change; a line whose window is empty (end before start, or its phase was deleted) blocks activation. The Forecast panel shows **Labor / Non-labor / Total**.
6. Add members (`Members`) so Owners/Contributors can edit.
7. Optionally set a **Contingency %** (0–100) and an **Estimate confidence** (Low / Medium / High) on `Edit`. Contingency is a risk reserve computed as a percentage of the priced forecast (labor + non-labor); the Forecast panel shows the base forecast and a separate **With contingency** total, so labor/non-labor breakdowns, run rates and the monthly phasing stay base figures. Baselines capture the contingency % / reserve and confidence in effect at activation, so later edits do not rewrite history. Portfolio shows a **Contingency** column, the portfolio total including contingency, a confidence badge per initiative and a count of low-confidence estimates; exports carry the same columns.
8. Optionally record the **Approved budget** (and a free-text **Budget fiscal year** such as `FY26`) on `Edit`; leave it blank until funding is approved. Details then shows the budget beside the amount the initiative is expected to cost – the live forecast including contingency while the plan is being shaped, switching to the **estimate at completion** (spent + remaining plan + contingency reserve) once a baseline exists and actuals are flowing – with the **remaining** amount, % of budget used and an **Over budget** / **Near budget** (≥ 90%) badge. Portfolio gets **Budget** and **Remaining** columns, an approved-budget tile with the portfolio-wide remaining and an over-budget count, and over-budget rows are highlighted; exports carry budget, fiscal year, remaining, % used and the over-budget flag. Budget changes are audited like any other initiative edit, and scenarios copy the budget so their comparison is against the same envelope.

### What-if scenarios

`Scenarios` on the initiative page (or `/Initiatives/{id}/Scenarios`) opens the side-by-side comparison. **New scenario from live plan** (Owner / Contributor) copies the plan – phases, allocations, non-labor lines, planning mode, target window, sizing, contingency % and confidence, participating BUs and members – into a Draft scenario that hangs off the initiative. Edit the scenario exactly like an initiative (it has its own Details page with a *What-if scenario* banner and a link back). Scenarios are private alternatives: they never appear on the Initiatives list, Portfolio, Capacity, search or exports, and they cannot be activated.

The comparison shows the live plan first and every scenario beside it – schedule (mode, phases, plan start/end), effort (total hours, people, then one *hours* row per resourcing class in use (Internal hours, Vendor hours, …) each broken down by the resource types in that class), cost (labor, vendor share, non-labor, forecast, contingency, with-contingency, confidence, unpriced lines) – with a green/red delta against the live plan under each scenario value. **Promote** (Owner; Admin) replaces the live plan's phases, allocations, non-labor lines, description and planning fields with a copy of the scenario's, then removes the scenario; the initiative keeps its identity, members, baselines, actuals and source mappings, and the audit log records before/after hours and cost. Promotion follows the normal scope-lock rules: it is only offered while the initiative is Draft or has an approved re-baseline (finalize the re-baseline afterwards to capture the promoted plan as the next baseline version). Deleting a Draft initiative also deletes its scenarios; a scenario itself can be deleted from its Details page at any time.

**Print / PDF** (or `/Initiatives/{id}/Scenarios/Print`, from the live plan or any of its scenarios) opens a chrome-free version of the comparison for steering packs: the same table with deltas but no links or Edit/Promote actions, followed by each plan's phase schedule (start, end, hours, cost per phase) and a generated-at timestamp. Use the browser's Print dialog → *Save as PDF*; with more than three columns choose landscape.

## 3. Activate and baseline (Owner)

1. When the forecast is complete, an Administrator clicks **Activate**; an Owner clicks **Request activation** (optional note) instead – administrators are e-mailed and decide on the initiative page or under **Approvals** (nav bar). **Approve & activate** activates on the spot; **Reject** (with a note) leaves the initiative in Draft and e-mails the requester. Guards: at least one phase and one allocation, valid dates, no unpriced lines.
2. Activation snapshots the forecast as **Baseline v1** and locks scope (phases/allocations become read-only).
3. Status transitions: Active → On hold → Active, Active → Complete / Cancelled. Complete/Cancelled initiatives drop off the default portfolio view.

### Re-baseline

1. Owner: **Request re-baseline** with a reason.
2. Administrator: **Approvals** (nav bar) → **Approve** (scope unlocks) or **Reject**.
3. Owner edits phases/allocations, then **Finalize** to snapshot **v2**. All versions remain in `Baselines` with deltas; variance is always measured against the *current* version. Baseline lines store the phase, business unit, resource type, seniority and vendor **names as of the snapshot**, so renaming a catalog entry later does not relabel historical baselines.

### Change requests

Formal scope / schedule / cost / resource changes on an **Active** initiative go through the **Changes** tab instead of an ad-hoc re-baseline:

1. Owner: **Raise change request** — type, title, what changes, reason, optional estimated cost / hours impact and (for schedule changes) the proposed target end. The live forecast, current baseline version and target end are recorded as the *before* snapshot; requests are numbered **CR-1, CR-2, …** per initiative. A pending request can be **withdrawn** by the Owner.
2. Administrator: **Approve** or **Reject** (with an optional note) from the Changes tab or the **Approvals** queue. Approving a change on an Active initiative opens an *approved* re-baseline (or joins the one already open), so scope unlocks immediately.
3. Owner applies the change to phases / allocations / non-labor, then **Finalize baseline vN+1**. Every approved change linked to that re-baseline becomes **Implemented**, capturing the *after* forecast, the resulting baseline version and the realised cost / hours impact (shown as *estimated / actual*).

Raising, deciding, withdrawing and implementing are audited (`ChangeRequest`, `ChangeRequestDecision`, `ChangeRequestImplemented`). Portfolio rows flag pending / approved changes (with the summed estimated pending cost impact) and the Portfolio and initiative exports include a **Change requests** table.

### Notes

The **Notes** tab on an initiative holds free-text notes (context, decisions, assumptions) with author and UTC timestamp; the `Baselines` page has a separate **Notes on baseline vN** panel under each selected version for sign-offs and caveats, and those notes also appear on the initiative's Notes tab with a *baseline vN* badge (the History tab shows a per-version note count). Users and Administrators add notes (max 4,000 characters); authors delete their own, Administrators delete any; Viewers read only. Adding and deleting are recorded in the audit log.

## 4. Load actuals (FinancePmo / Administrator)

1. Map each initiative to its external project: initiative page → **Source mappings** → source (`planview`, `jira`, `csv`) + external project id.
2. Prepare a CSV:

   ```text
   ExternalProjectId,ExternalPersonId,WorkDate,Hours[,Cost][,Reference]
   PV-1001,E12345,2026-03-04,7.5,,
   ```

   - `WorkDate` is `yyyy-MM-dd`; `Hours` > 0.
   - `Cost` is optional. Blank → priced from the person's roster attributes and the rate card in effect on `WorkDate`; supplied → used as-is.
   - `Reference` is optional; blank defaults to `<file>#<line>`. `(Source, Reference)` is the idempotency key – re-importing the same file skips already-loaded rows.
3. `Actuals → Import`. Files with any invalid row are rejected as a whole (nothing is written). Files over 10 MB are refused.
4. Review the import summary: imported / skipped / **unmapped** counts. A row's person is resolved by roster **external ID** first; failing that, if the row's project maps to an initiative and `ExternalPersonId` equals the display name of exactly one person **named on that initiative's allocations**, that person is used. Unmapped rows (unknown project or person) sit in `Actuals → Unmapped`; assign them to an initiative/person there (the same name fallback applies once the project is mapped), or fix the mapping/roster and re-import.
5. Rows flagged **Unpriced actuals** have no rate for the person's attributes on that date – add the rate to a published card.
6. Add **adjustments** (category, hours/cost with a reason) on the initiative's Actuals page for invoices, accruals or corrections. Use a non-labor category (e.g. *Software license*) for vendor invoices so they land against the non-labor baseline in the variance view.

## 5. Track variance

- Initiative → **Variance**: current baseline vs. mapped actuals + adjustments, by phase, resource type and cost category (labor vs. software license etc.), with the threshold flag (initiative-level `VarianceThresholdPct` or the global default). When the baseline has named allocations a **By person** table compares each named person's baseline hours/cost with the actuals recorded against them; unassigned baseline lines are grouped as *Unassigned – <resource type>*.
- **Portfolio** (`/Portfolio`): one row per initiative with live forecast (internal/vendor/non-labor split), baseline, actuals, variance %, burn bar and badges (*Over threshold*, *Unpriced forecast/actuals*, *Re-baseline pending*), plus rollups by **sponsor BU** and status, and labor splits by **resourcing BU** (where the allocated people come from) and by **vendor**. Filter by status or BU; tick *Include Complete/Cancelled* to see closed work.
- **Cost by month**: Initiative → **Costs** tab and the **Portfolio** page show forecast, baseline and actual cost per calendar month (bar chart + table with cumulative columns and per-year subtotals). Labor is spread across each phase by calendar days; recurring non-labor lines are placed at the start of each billing period; actuals fall in the month of the work date (adjustments: the month they were recorded). Baseline months use the phases' *current* dates, so moving a phase shifts the baseline profile with it while the baseline total stays fixed.
- **Cost by fiscal year and quarter**: beneath the monthly table on the Costs tab, the Portfolio page and the one-pager, the same months are rolled into fiscal-year rows with quarter rows under each (FY start month from `Admin → Work calendar`), showing hours, labor, non-labor, forecast, **Capex / Opex**, baseline, Δ vs. baseline and actual. Every allocation and non-labor line carries a **Capex %** (0–100; 0 = all Opex, 100 = all Capex, e.g. 60 puts 60 % of the line in Capex and 40 % in Opex). New labor lines are prefilled from their resourcing class's default under `Admin → Resourcing classes` (Internal 70 / Vendor 100 out of the box); non-labor lines default to 0 unless the catalog item sets one. The Capex share is rounded to cents and Opex is the remainder, so the two always add up to the line's cost. Baselines snapshot the percentage and scenarios copy it, so history and comparisons keep the treatment in force at the time.
- **Capacity** (top nav, `g y`): planned hours per resource type and month across all open initiatives (filters as on Portfolio), coloured by demand ÷ roster supply. Supply = active People with that resource type × working hours in the month (Mon–Fri minus Admin → Work calendar holidays, at the configured hours/day). Red cells exceed supply; hatched cells have demand but nobody of that type on the roster. Hover a cell to see which initiatives drive it; Export gives the cells and per-initiative breakdown as CSV/XLSX. Switch the view to **People** for one row per named roster person (demand from the allocations naming them vs. *that person's* working hours, red above 100 %) plus an *Unassigned – <resource type>* row per type for generic allocations – open staffing work rather than an over-allocation. Export follows the selected view.
- **Export** (Administrator / FinancePmo): *Export CSV/XLSX* on the portfolio (honours current filters) or on an initiative (summary incl. participating BUs, forecast and baseline lines with BU, vendor, Capex % and Capex / Opex cost, *By month* phasing, *By fiscal period* (FY and quarter rows with Capex / Opex and baseline splits), variance, actuals, adjustments). The portfolio export also has *By month* / *By fiscal period* (all initiatives combined) and *Initiative by month* / *Initiative by fiscal period* (one row per initiative per period) tables. Exports are audited.

## 6. Audit

`Audit` lists every create/update/delete/publish/activate/import/export event with actor, timestamp and entity link. Filter by entity type and id.

## 7. Working with tables

- **Sort**: click a column header (or focus it and press Enter/Space) to sort ascending; click again for descending. Numbers, currency, percentages and dates sort numerically/chronologically; text sorts case-insensitively. Sorting is presentation-level – it re-orders the rows currently on the page only, so on filtered pages (e.g. Actuals) apply the filter first.
- **Server-side paging (Portfolio, Audit)**: these lists are paged by the server – 25/50/100 rows per page (default 25 for Portfolio, 50 for Audit) with Previous/Next and page numbers under the table; filters, sort, page and page size are all in the URL, so a page can be bookmarked or shared. Portfolio column headers sort the whole filtered portfolio (not just the visible page; initiatives without a value, e.g. no baseline, sink to the bottom), and the tiles, totals row, monthly chart and rollups always cover every matching initiative, as do exports. Audit is always newest first.
- **Select rows**: tables with a checkbox column (rate-card entries, People, Business units, Resource types, Disciplines, Vendors, Cost catalog, Holidays, Actuals entries, an initiative's Allocations and Non-labor costs) have a header *select all* that applies to the rows currently shown; the action bar shows *N selected* and its buttons are disabled until something is selected. Destructive actions ask for one confirmation.
- **Bulk actions**: *Save selected* / *Adjust by %* / *Delete selected* on rate-card entries (draft and published cards only; retired cards are read-only; rates must be ≥ 0); *Activate* / *Deactivate* / *Delete selected* on admin catalogs; *Assign selected* to an initiative and/or person on Actuals entries; *Delete selected* on allocations and non-labor costs (draft/unlocked initiatives only). Each changed or deleted row is audited individually.
- **Skipped rows**: guarded rows are never silently deleted – a catalog row that is still referenced (e.g. a BU used by initiatives, a person with imported actuals) is skipped and the result message says how many were deleted and how many were skipped and why. Deactivate instead to hide them from new selections. A single invalid value in a bulk save (e.g. a negative rate) rejects the whole save so nothing is half-applied.

## 8. Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| Forecast line shows **Unpriced** | No published rate-card entry exactly matches resource type + seniority + location + class (+ vendor) on the phase start date (seniority matches by catalog level, so *Senior* and a vendor's *Level 3* are different rows); rates are global, so the allocation's business unit is irrelevant. Add the entry; there is no fallback pricing by design. |
| New resource type / rate-card row not selectable on *Add allocation* | The rate card must be **Published** (or retired with an end date) with an effective window covering the phase start, and the resource type must be active. The allocation form narrows each dropdown as you pick the previous one – change phase / resource type first. |
| **Activate** is disabled | Check the guard list on the page: phases, allocations, dates, unpriced lines. |
| Import rejected | The error lists the first 10 offending lines. Fix the file and re-upload; nothing was written. |
| Rows imported as **unmapped** | Add a source mapping for the project id and/or a person with that external id, then assign in *Unmapped* or re-import. |
| Local dev DB errors after pulling | Development uses SQLite with `EnsureCreated`; delete `src/InitiativeScoping.Web/initiative-scoping.dev.db*` and restart. |
| 403 *Access denied* | Your role (`Admin → Users`; `Auth:Dev:Roles` locally) lacks the permission – see the roles table above. |
| Redirected to *Request access* | You have no role yet (or your account is disabled/pending). Request access and ask an Admin to approve it under `Admin → Users`. |
